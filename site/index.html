> skill + cli · zéro dépendance · node 18+

Un essaim d'agents de code sur un seul tableau noir.█

Un coordinateur découpe. Des workers nommés construisent en parallèle. Un vérificateur indépendant lance les tests et juge. Rien n'est considéré comme fait avant que ce juge ait parlé.

Mure est l'idée du /swarm de Google Antigravity, transposée aux harnais dont les agents ne savent pas dormir sur un tableau — OpenCode, Claude Code, Codex CLI, Gemini CLI, Cursor.

[01]

Trois règles, et rien d'autre

C'est toute l'astuce : pas de polling, pas de processus endormi. Antigravity peut parquer un agent en veille sur un tableau ; ici, « endormi » veut dire « aucun processus ».

  1. 01

    Le tableau est la seule vérité

    Chaque consigne, question, rapport et verdict est un post numéroté, horodaté, adressé, dans un journal append-only. Ce qui n'est pas sur le tableau n'a pas eu lieu.

  2. 02

    La mention est le seul réveil

    Un membre n'agit que s'il a un post non lu qui lui est adressé. Sans post, il ne tourne pas — et ne coûte rien. On ne simule jamais un agent endormi avec une boucle d'attente.

  3. 03

    Le coordinateur ne code pas

    Il découpe, route, répond aux questions et tranche la clôture. S'il implémente lui-même la pièce la plus facile, ce n'est plus un essaim : c'est un agent seul avec du décor.

> quand l'utiliser — et quand s'abstenir

Une tâche annexe pendant que vous travaillez
un seul sous-agent
Un problème dur et fortement couplé (un bug, un algorithme)
un agent, ou des relances ciblées
Un travail large qui se découpe en morceaux disjoints
mure
Un chantier de plusieurs jours avec jalons
un plan, puis des runs Mure successifs

refusé Un changement sur un seul fichier, une question à laquelle vous pouvez répondre seul, un travail où chaque morceau touche le même fichier, ou tout ce pour quoi vous ne savez pas énoncer une commande de vérification.

[02]

La boucle en sept étapes

Dans l'ordre. On ne saute ni la première ni la sixième. Chaque commande écrit son état dans le .mure/ du dépôt courant : lancez-la depuis le projet sur lequel vous travaillez.

  1. 01

    Énoncer l'objectif et la vérification

    Une phrase, et la commande qui prouve le travail (npm test, pytest -q, go test ./..., tsc --noEmit). Un essaim sans commande de vérification produit de la prose confiante, pas du code qui marche.

  2. 02

    Créer l'essaim

    --verify est recopiée dans le prompt de chaque membre : personne n'a à deviner ce que « fait » veut dire. --max-parallel est un frein de quota, pas une limite technique.

  3. 03

    Découper en morceaux qui ne se chevauchent pas

    Une pièce par fichier, par paquet, par module, par question. On nomme le membre d'après sa pièce : @parser, @api-tests, @docs. --owns est réellement appliqué : mure scope sort en erreur sur une violation.

  4. 04

    Poster le brief, puis dispatcher

    mure prompt @x rend le brief plus tous les posts non lus, et avance le curseur : le texte que vous collez est la livraison. On ne le reformule pas, on ne le résume pas, on ne le colle pas dans deux agents.

  5. 05

    Collecter et router

    Chaque tour se termine par un post unique : report, ou question si le membre est bloqué. Ensuite, le processus s'arrête. On réveille le vérificateur par une note, jamais par un brief.

  6. 06

    Vérifier avant de croire

    Le vérificateur lit les diffs, lance la vraie commande et poste un verdict par worker. Un rejet n'est pas une semonce, c'est un élément de travail : on re-dispatche le même worker.

  7. 07

    Clore et rapporter

    close refuse tant qu'une porte est ouverte. Puis on rapporte : ce qui a été vérifié et par quelle commande, ce qui ne l'a pas été, les contradictions, où sont les fichiers, et ce que veut dire une réserve.

[03]

Le dépôt est le skill

Le dossier doit être visible sous le nom mure, avec SKILL.md à sa racine. Le script crée une jonction (Windows) ou un lien symbolique vers ~/.config/opencode/skills/mure, ~/.claude/skills/mure et ~/.agents/skills/mure : un git pull met tous les harnais à jour d'un coup. Supprimez ceux que vous n'utilisez pas.

Prérequis : Node 18+ (node scripts/mure.mjs help doit afficher la liste des commandes). Git est optionnel, sauf pour mure scope, mure worktree et la baseline de dispatch.

$ installer

git clone https://github.com/t12lve/mure.git
cd mure

# macOS / Linux
./install.sh

# Windows
.\install.ps1

$ cinq minutes

cd mon-projet
M="node /chemin/vers/mure/scripts/mure.mjs"

# 1. l'essaim, et la preuve du travail
$M init validation --goal "Add input validation" \
  --verify "npm test" --max-parallel 2 --worktrees

# 2. un membre par morceau étanche
$M member add "@parser" --role worker \
  --owns "src/parser.js,test/parser.test.js" \
  --must-not "src/api.js" --done "parse() throws"

$M member add "@verifier" --role verifier \
  --watches "@parser" --done "suite run, diffs read"

# 3. le brief va aux workers, pas au vérificateur
$M post --from "@coordinator" --to "@parser" \
  --kind brief --body "One file pair. Report when green."

# 4. qui a du travail ?
$M runnable
$M prompt "@parser"   # à donner tel quel

[05]

Trois portes qui refusent

L'outil dit non à votre place. C'est là qu'il gagne son coût : la discipline n'est pas dans la doc, elle est dans le code, avec les codes de sortie qui vont avec.

Porte de vérification

Un verdict doit citer un rapport, porter un motif obligatoire, et une réserve doit être citable. verdict refuse un non-vérificateur, et un worker ne peut pas poster de verdict.

exit 1

Porte de clôture

close refuse sur une question ouverte, un worker qui n'a jamais rapporté, un rapport jamais jugé alors qu'un vérificateur existe, un verdict rejected ou needs-info, ou un block non résolu.

exit 1

Porte de périmètre

Chaque dispatch enregistre une baseline de l'arbre. scope ne rend que ce qui a changé depuis, et sort en erreur si un fichier hors --owns a bougé : un fichier déjà sale avant le tour n'est pas imputé au worker.

exit 3

[06]

Ce qui est vérifié, et ce qui ne l'est pas

Testé réellement, sur Windows, Node 22 : création d'essaim, membres, posts, curseurs, prompt, scope avec baseline, worktrees, verdicts, graphe mermaid, doctor, porte de clôture. Un essaim réel de deux workers et un vérificateur a tourné en sous-agents OpenCode et produit un tableau complet. 23 tests automatisés, chacun vérifié par mutation : inverser la garde qu'il protège fait tomber exactement le test correspondant. CI sur Linux, macOS et Windows, Node 18 à 22.

La relecture qui a suivi le premier essai a trouvé quatre défauts réels, tous corrigés et couverts : les rôles n'étaient pas appliqués, @all adressait les membres tués, un nom de membre avec une espace cassait le graphe, et un block rendait la clôture impossible pour toujours.

! limites connues, écrites plutôt que cachées

  • En arbre partagé, mure scope ne peut pas attribuer les fichiers entre deux workers concurrents — utilisez --worktrees, ou dispatchez un worker à la fois.
  • prompt avance le curseur : un prompt perdu entre l'affichage et la livraison se récupère avec mure cursor @x --reset.
  • La fusion des branches mure/<slug>/<membre> est laissée au coordinateur, pas à l'outil.
  • Un tour perdu est indistinguable d'un tour jamais lancé.
